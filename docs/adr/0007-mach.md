# 0007 - Mach as a foundation option: rejected, ideas borrowed

- Status: accepted
- Date: 2026-11-26
- Decides for: 0.10 (research), confirms 0001 (window/GL) and 0006 (threading)
- Reopens: nothing. ADR 0001 still stands for the window and GL; ADR 0006 still
  stands for the threading model.

## Verdict

**Reject wholesale, borrow ideas.** Mach is a promising engine, but adopting it
would mean moving the whole project onto a nominated 0.18-dev Zig toolchain and
replacing the window/GPU layers this project has already measured and shipped.
The spike could not even get its build to run on our toolchain, and the package
server is unreachable from this network.

## Compatibility matrix

| | Mach `main` | Mach v0.5 (last tag) | This project |
|---|---|---|---|
| Zig target | nominated nightly `2026.10.22-mach` = `0.18.0-dev.935` | `2024.11.0-mach` | **stable 0.17.1** |
| Windowing | own (`mach.core`) | GLFW | SDL3 |
| GPU | `sysgpu` (WebGPU-shaped, own backend) | WebGPU-shaped | GL 4.6 core via zigglgen |
| Platform story | macOS/Metal and mobile in scope | same | Linux/X11 only, by scope |
| Package source | `pkg.hexops.org` (Forgejo, GitHub mirror) | same | `zig fetch` + system libs |
| Builds on 0.17.1 | **no** | **no** (see below) | yes |

## The spike, with real output

Run on burken (Zig 0.17.1):

1. `zig fetch --save https://pkg.hexops.org/pkg/hexops/mach/` produced nothing:
   the host resolves (`pkg.hexops.org` -> `178.104.111.154`) but never answers.

```
$ curl --max-time 3 https://pkg.hexops.org/zig/index.json
curl: (28) Operation timed out after 3002 milliseconds with 0 bytes received
$ curl --max-time 3 https://raw.githubusercontent.com/hexops/mach/main/README.md
github http 200
```

   So the package server, not our network in general, is the blocker.

2. The GitHub mirror does fetch, so the version question could be tested
   directly:

```
$ zig fetch --save https://github.com/hexops/mach/archive/refs/heads/main.tar.gz
    .mach = .{
        .url = "https://github.com/hexops/mach/archive/refs/heads/main.tar.gz",
        .hash = "mach-0.5.0-jXwHfcPbNAD161AV-21pEhz-o6nFBLOdcP6P8bfmmc87",
    },
```

3. Wiring `mach` into a trivial exe and building it on 0.17.1 fails inside
   Mach's own `build.zig`, before any of our code is involved:

```
zig-pkg/mach-0.5.0-.../build.zig:176:23: error: no field named 'args' in struct 'Build'
        if (b.args) |args| run_cmd.addArgs(args);
zig-pkg/mach-0.5.0-.../build.zig:534:30: error: root source file struct 'Build'
  has no member named 'GeneratedFile'
    generated_file: std.Build.GeneratedFile,
```

   That is the answer to "can any Mach component be consumed on stable 0.17.1":
   no, not even the build script.

## What we would gain, and what it would cost

Gain: macOS/Metal and mobile in one move, `sysaudio`, DPI/UI-scale handling and
an opinionated app lifecycle. None of those are in the PoC scope; the PoC is
Linux/X11, no audio, and one window at a fixed DPI.

Cost: the whole project moves to a nominated nightly that changes every ~6
weeks, with pre-1.0 API breaks; ADR 0001 (SDL3) and ADR 0002 (GL texture array)
would be thrown away, and the threading model in ADR 0006 would have to be
re-checked against whatever `std.Io` looks like in that tree. Measured against
that, the PoC gets nothing it needs.

## What we borrow anyway

- **App lifecycle shape**: a single `App` struct owning window, input, renderer
  and the run loop, which is what `src/app.zig` already looks like.
- **Input abstraction**: keep the engine's `Input` (held keys plus per-frame
  edges) rather than letting raw SDL events reach gameplay, which is what 1.9
  and 1.10 rely on.
- **DPI handling** is a real gap for us: our window is a fixed pixel size and
  does not listen to scale changes. Recorded here so a future task can copy
  Mach's approach without adopting the dependency.

## Consequences

- ADR 0001 stays: SDL3 + GL 4.6, measured at 120 fps on the target machine.
- ADR 0006 stays: `std.Io` + `Group.async`, measured at 8.5 ms worst frame while
  streaming.
- Nothing in phase 1 or 2 changes because of this decision, which is exactly why
  the research was worth doing before the build phase rather than after.
